# 接口与接入说明

## 当前边界

前端是可交互的浏览器本地原型：Pinia 统一管理状态、localStorage 留存体验数据。演示会员初始有 120 积分；可模拟购买入账、积分兑换、用券下单、门店接单、制作、取餐与商品售罄。未发生真实扣款。

注册登录已通过前端调用 Spring Boot，账号写入 MySQL `users` 表；具体启动及权限说明见 [注册登录与本地联调](注册登录与本地联调.md)。购物、积分、券和订单仍为按账号隔离的本地模拟；商品 controller 仍返回静态目录。

## 已实现的后端接口

| 接口 | 权限 | 结果 |
| --- | --- | --- |
| GET /api/health | 公开 | 应用健康与 scaffold 阶段标记，不代表数据库连通 |
| GET /api/products | 公开 | 六款静态商品样例，价格单位分 |
| GET /api/csrf | 公开 | CSRF token 与请求头名称 |
| POST /api/auth/register | 公开，需 CSRF | 注册账号并创建会员账户 |
| POST /api/auth/login | 公开，需 CSRF | 验证账号密码并建立 Session |
| GET /api/auth/me | 公开 | 当前账号或 null |
| POST /api/auth/logout | 需 CSRF | 清理会话 |
| POST /api/auth/shopping-access | 已登录，需 CSRF | 检查购物身份，不创建订单 |
| POST /api/admin/access | STAFF / ADMIN，需 CSRF | 检查门店操作权限 |

其他 API 默认需认证，`/api/admin/**` 要求 STAFF / ADMIN 角色。无默认用户；注册仅授予 CUSTOMER。不得仅根据前端工作台地址判断用户权限。

顾客界面导航不包含门店工作台，“我的”个人中心使用 `/me`。员工入口使用 `/staff/login`；`/admin` 允许公开只读浏览布局，操作按钮需要服务端返回的员工身份并通过权限检查接口。后续新增管理 API 时继续细分管理员专属营销等操作。

## 下一阶段接入顺序

1. 已完成用户注册登录、会话与角色数据库映射；后续业务接口继续从服务端获取当前用户。
2. catalog 应用服务与 MyBatis mapper 替换静态商品，扩展规格、选项、售卖状态。
3. POST /api/orders/quote：服务器计价、可用券判断；创建订单时再校验一次。
4. POST /api/orders：使用 OrderContracts.Create，客户端只传商品、规格、选项和数量，不传可信价格。
5. 接入 PaymentGateway 的真实实现，验签、金额检查、支付查询与关单补偿。
6. 在事务中实现积分入账及兑换，使用数据库唯一键、条件更新与固定加锁顺序。
7. 接入会员、订单查询和后台操作，移除前端本地演示写入。

统一响应为 `{code,message,data}`。写请求先取 GET /api/csrf 返回的 token，携带在返回的 headerName 对应请求头中，并发送同源会话 Cookie。后端保留 Spring Security 默认令牌处理机制；不直接读取 cookie 值替代接口返回的 token。

## 业务约束

- 兑换请求号、支付业务号、积分流水幂等键均有唯一约束。
- 金额使用整数分；券门槛以优惠前商品总额计算；积分以最终实付整元计算。
- 数据库库存和账户余额才是正式权威来源；浏览器中不能实现真实并发事务。
- 退款与锁券、取消、超时关单的正式实现仍按项目实施方案完成，当前 UI 不模拟退款成功。
- 先实现订单闭环，再补营业统计、会员查询、券模板编辑与退款审核页面。
