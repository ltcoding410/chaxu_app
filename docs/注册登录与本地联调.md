# 注册登录与本地联调

## 已实现的边界

- 注册信息写入已有业务主表 `users`，密码采用 BCrypt 哈希；注册时同时创建 CUSTOMER 角色关系和零积分会员账户。
- `database/chaxu_user.sql` 是之前的独立草案，不用于本次认证。已在该表手工创建的账号不会自动变成 `users` 账号，需重新注册。
- Flyway 新增 V3；不修改已执行的 V1/V2。启用 mysql 模式时自动新增 username 列、允许未绑定手机号，并保留原有业务外键。数据库必须提前存在；如手工建过与迁移重名的业务表，先备份并核对 Flyway 历史，不要删除表或盲目 baseline。
- 注册、登录、退出、会话恢复是后端真实功能；购物、积分、优惠券和订单仍是本地模拟，按账号 ID 分区保存，不代表真实支付或服务端订单持久化。
- 不导入旧 `chaxu-demo-v1` 共享体验数据，以免泄露给新注册用户。游客状态展示空的个人数据；注册不自动登录。

## Windows 后端连接 Ubuntu 数据库

先在单独的 PowerShell 窗口建立隧道并保持运行（Navicat 内置隧道不能供 Java 共用）：

```powershell
ssh -N -L 13306:127.0.0.1:3306 ltcoding@192.168.245.129
```

在 IDEA 后端运行配置里设置这些环境变量，启动 `ChaxuApplication`：

```text
SPRING_PROFILES_ACTIVE=mysql
SERVER_PORT=8080
DB_USERNAME=chaxu_app
DB_PASSWORD=你设置的数据库密码
```

默认 JDBC 地址是 `jdbc:mysql://127.0.0.1:13306/chaxu?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai`。如果数据库地址不同，通过 `DB_URL` 覆盖。Ubuntu 同机部署应将端口改为 3306。

也可以通过终端启动（密码通过输入框读取）：

```powershell
cd backend
$env:SPRING_PROFILES_ACTIVE = 'mysql'
$env:SERVER_PORT = '8080'
$dbCredential = Get-Credential -UserName 'chaxu_app' -Message '输入数据库密码'
$env:DB_PASSWORD = $dbCredential.GetNetworkCredential().Password
mvn spring-boot:run
```

另开终端在项目根目录运行 `npm run dev`。Vite 默认代理 `/api` 到 `http://127.0.0.1:8080`；如需调整，复制根目录 `.env.example` 为 `.env.local` 并设置 `BACKEND_URL`，然后重启 Vite。

`backend/.env.example` 不会自动加载。不要将真实密码提交到配置文件。不要把后端直接切到 demo 模式来绕过账号服务：demo 可浏览，但注册登录返回 503 提示。

## 页面与权限

| 操作 | 游客 | 顾客 | STAFF / ADMIN |
|---|---|---|---|
| 浏览饮品、规格、各页面布局 | 允许 | 允许 | 允许 |
| 查看本人账号、购物袋与本地订单 | 不展示个人数据 | 允许 | 允许 |
| 加购物袋、修改数量、模拟下单、兑换 | 引导登录 | 允许 | 允许 |
| 门店处理订单、商品售罄操作 | 禁用 | 禁用 | 允许本地演示 |
| `/api/admin/**` | 401 | 403 | 允许 |

所有页面均可浏览，包括 `/admin` 的只读布局；门店页面不展示其他账号的真实经营数据。员工权限由数据库管理员分配，不接受注册请求中的 roles、enabled 等字段。

授权已有账号为店员的示例（由数据库管理员按实际账号执行）：

```sql
INSERT INTO user_roles(user_id, role_id)
SELECT u.id, r.id FROM users u CROSS JOIN roles r
WHERE u.username = '实际员工账号' AND r.code = 'STAFF'
AND NOT EXISTS (
  SELECT 1 FROM user_roles ur WHERE ur.user_id = u.id AND ur.role_id = r.id
);
```

角色变更后退出并重新登录。没有默认管理员密码。

## 认证与过滤器

- Spring Security 过滤器链恢复服务端 Session，按 API 路径和角色授权；前端按钮限制不能替代后端权限校验。
- Session Cookie 为 HttpOnly、SameSite=Lax，闲置 30 分钟过期；登录更换既有 Session ID，退出失效会话。生产 HTTPS 设置 `SESSION_COOKIE_SECURE=true`。
- 写请求保留 CSRF；前端每次写请求前通过 `GET /api/csrf` 获取 token，在响应指定的 header 中携带。登录成功清除旧 token，退出由 Spring Security 清理。
- 注册/登录每来源 IP 合计每分钟最多 20 次，超出返回 429。当前为单实例内存限流；反向代理后来源可能共用额度，正式多实例部署应在可信代理/网关使用共享限流。账号禁用及角色调整在重新登录时生效，现有会话按退出/超时结束。
- 每次购物动作调用已认证的 `/api/auth/shopping-access`；发现过期会话跳转登录。它只验证身份，不是实际下单接口。真实购物服务上线时必须在业务接口按当前用户校验价格、库存、订单归属，不能信任浏览器数据。
- 未登录 API 返回 401、权限/CSRF 校验失败返回 403、注册冲突 409、参数错误 400、demo 账号服务未启用 503。

## 验证

`mvn test` 使用独立 H2 测试库验证真实 SQL 写库与认证，不访问虚拟机。测试覆盖注册事务、密码哈希、唯一账号、越权字段、错误密码、禁用账号、CSRF、会话更新、退出及限流。

浏览器联调可以使用独立 H2 数据库检查交互，但不能替代真实 MySQL 上 V1–V3 迁移的部署验收；真实 MySQL 验收应在已建立隧道并设置运行参数后执行。
